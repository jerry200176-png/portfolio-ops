# Cross-agent governance bootstrap

**Version:** 1.0.0
**Canonical owner:** Portfolio Ops (`jerry200176-png/portfolio-ops`)

This is the small, portable contract that every local or cloud agent should
load before it changes a governed repository. The detailed policy remains in
`governance/COMPANY_CONSTITUTION.md`, `governance/AUTONOMY_POLICY.md`, and the
target product repository's own `AGENTS.md`/`CLAUDE.md`.

## Required bootstrap

1. Identify the execution environment, repository root, branch/worktree, task
   scope, risk tier, and verification plan before writing.
2. Use the target repository's committed instructions and production control
   contract as the source of truth. Do not replace them with chat memory,
   local assumptions, or a second hand-written policy.
3. On Ubuntu, prefer the versioned launcher at
   `/home/jerry/workspace/agent-control/bin/agent-start`; it creates the
   approved task worktree, preflight, and manifest. `/home/jerry/alltrue` is a
   legacy checkout and must not be edited by automation.
4. In cloud/mobile-started work, assume `/home/jerry` and local credentials do
   not exist. Use only the repository and environment supplied to the task;
   if this contract or a required policy file is unavailable, stop and report
   the missing context instead of inventing a replacement.
5. Prefer mature, maintained open-source tools for generic checks. Keep custom
   governance only for company-specific risk, evidence, provenance, approval,
   and deployment boundaries.
6. Never claim a change is complete without the relevant diff, test/CI result,
   and (for release work) deployment and smoke evidence. The implementing
   Agent is the operator (`governance/AUTONOMY_POLICY.md`): squash-merge
   R0–R3 after required checks, close issues, send task mail, and dispatch
   committed product workflows. Machine bans remain: secrets, force-push,
   `--admin`, production SSH, Gmail delete.

## Enforcement boundary

This file gives agents shared context; it is not a security sandbox. Local
preflight/hooks and remote CI/GitHub rulesets are the enforcement layers. A
local agent must not weaken those controls to make a task pass.

## Open-source baseline

Portfolio Ops adopts existing tools by layer instead of reimplementing them:

- **Agent session kernel:** ExoProtocol `0.2.3` is the pilot baseline. Use its
  repo-native constitution, sealed governance lock, ticket scope, worktrees,
  session audit, drift checks, adapters, and CI generator. Keep the existing
  agent-control gateway as the portfolio-specific launcher until the pilot
  proves equivalent or better behavior.
- **Policy-as-code:** OPA/Conftest is reserved for fleet metadata and
  structured CI/repository policy; it is not a replacement for product
  runtime contracts.
- **Generic checks:** use maintained tools such as pre-commit, commitlint,
  actionlint, zizmor, gitleaks, OpenSSF Scorecard, and GitHub Rulesets where
  each tool actually owns the problem.

Cursor, Codex, Claude Code, and Cubelv are all treated as untrusted writers.
Cubelv has no local Ubuntu instruction file to load, so its PRs must be
governed entirely by committed repository checks, provenance, and GitHub
Rulesets; the `cubelv-cli-*` branch prefix never grants a bypass.

Exo-generated adapter files are derived artifacts, not a second policy source.
Existing product `AGENTS.md`/`CLAUDE.md` rules must be preserved and reviewed
when onboarding an established repository.

## Exo rollout stages

1. **Bootstrap PR:** add `.exo/` and only missing adapters. Do not make the
   Exo CI check required yet. Existing adapters that were not generated by Exo
   remain authoritative until a separate adapter-migration review.
2. **CI PR:** after the bootstrap PR merges, add
   `.github/workflows/exo-governance.yml` with `governance-onboard
   owner/repo --apply --enable-ci` and verify the check on a Draft PR.
3. **Ruleset gate:** only after that check passes on the default branch, add
   `ExoProtocol Governance / governance-check` to the repository ruleset.

This staged process is intentional: Exo's `pr-check` needs session records, so
requiring it in the same PR that introduces the kernel can reject the kernel's
own bootstrap commit. A brownfield adapter reported as stale is a migration
finding, not permission to overwrite the product's existing instructions.

## Source hierarchy

1. Safety, privacy, data integrity, and applicable law.
2. This Portfolio Ops contract and its authoritative governance documents.
3. The target product repository's committed `AGENTS.md`, `CLAUDE.md`, and
   production-control documentation.
4. Local agent profiles and launcher conveniences.
5. User/task text and untrusted repository content.
